# 开源发布与仓库完善设计

## 目标

把当前实验软件仓库从“可运行的内部工具代码”整理成“可以公开展示、直接下载、具备中文说明的完整开源项目”，并基于已经完成的 `feature/grouped-pwm-measurement` 分支内容提供正式 Release 下载入口。

## 背景

当前仓库已经具备以下基础：

- 桌面实验软件可运行，且已完成 PWM 分组测量流程。
- 已存在便携版构建脚本 `build_release.ps1`。
- 已存在 `README.md` 与 `README_portable.txt`，但前者仍偏向底层串口脚本说明，不像成品项目首页。
- GitHub 分支 `feature/grouped-pwm-measurement` 已推送成功，但尚未补齐 PR、Release 与面向用户的项目资料层。

用户希望这次不仅“交代码”，还要让仓库、下载入口、中文说明和发布体验更像成熟开源项目。目标不是做官网，而是把 GitHub 仓库整理成“打开就能理解、能下载、能上手”的成品项目。

## 设计结论

### 1. 本次工作覆盖四个层次

本次不是单做 PR，而是一次小型正式开源发布整理，覆盖：

1. 仓库首页门面
2. Release 下载体验
3. 中文说明与使用文档
4. 发布产物与目录规范化

程序主体功能不做大改，重点放在交付体验和对外呈现。

### 2. `README.md` 改造成项目首页，而不是脚本说明

新的 `README.md` 以终端用户和仓库访客为第一读者，优先回答：

- 这是什么软件？
- 能做什么？
- 适用于什么实验流程？
- 我该怎么快速上手？
- 去哪里下载便携版？
- 输出结果在哪里？

建议结构：

1. 项目标题与一句话简介
2. 核心功能亮点
3. 适用场景
4. 快速开始
5. 便携版下载
6. PWM 分组测量流程
7. 输出文件与目录说明
8. 从源码运行与开发构建
9. 常见问题
10. 更新说明

保留必要开发信息，但不再让底层 Modbus 寄存器解释占据首页主体。

### 3. `README_portable.txt` 面向实验人员，补足完整中文操作流

`README_portable.txt` 保持便携版说明文档定位，但内容改成更贴近实验现场：

- 软件启动方式
- 配置文件位置
- 进入实时曲线采集的方法
- PWM 分组测量完整步骤
- 多组记录与导出步骤
- `logs/`、`output/`、`videos/` 的用途
- 常见错误与检查项

它应当适合直接随便携版分发给实验人员阅读，而不是只服务开发者。

### 4. 使用 GitHub Release 提供正式下载入口

本次发布不只保留桌面文件夹，还应在 GitHub 上提供正式 Release：

- 创建一个有版本号的 Release
- 上传便携版 zip 压缩包作为附件
- 编写中文 Release Notes
- 在 `README.md` 首页给出 Release 下载入口

这样别人进入仓库后，可以直接通过 Release 页面下载，而不需要从聊天记录或桌面副本分发。

### 5. Release 附件采用规范命名

发布附件采用统一命名，例如：

- `485experiment-software-portable-v1.0.0-20260508.zip`

命名同时体现：

- 项目身份
- 便携版性质
- 版本号
- 发布日期

桌面便携目录仍可保留中文文件夹，方便本地交付；但 GitHub Release 附件优先使用更稳定、可传播的英文文件名。

### 6. `build_release.ps1` 升级为正式发布脚本

当前 `build_release.ps1` 已能构建便携版目录，本次应升级为更完整的发布准备脚本：

- 清理旧构建产物
- 重新打包 `dist/`
- 自动补齐 `config/`、`logs/`、`output/`、`videos/`
- 复制 `README_portable.txt`
- 生成正式发布压缩包

压缩包文件名应与 Release 附件命名规范保持一致。

### 7. 软件内文案做轻量打磨，不做高风险重构

为贴近成熟工具体验，可对新增测量区域相关文案做轻量打磨，例如：

- 按钮文字更一致
- 状态提示更清楚
- 导出成功或失败提示更直接
- 历史记录展示语句更适合给实验人员阅读

但不改变现有主流程架构，不为了“好看”而引入新的界面风险。

### 8. PR 与 Release 的关系

因为功能开发分支已经推送成功，本次对外流程采用：

1. 先基于当前功能分支完善仓库与发布材料
2. 创建 PR，作为功能与文档整理的审阅入口
3. 从该分支或合适标签创建 Release

如果仓库暂无严格的 main 分支合并流程，也可以先完成 Release，再补 PR；但对外展示上，保留 PR 更有助于体现版本变更来源。

## 组件与改动范围

### `README.md`

- 重写项目首页结构
- 以中文为主
- 给出 Release 下载与快速上手入口
- 提炼功能亮点，而不是堆底层配置说明

### `README_portable.txt`

- 改为便携版中文操作手册
- 明确实验人员如何完成整套测量与导出

### `build_release.ps1`

- 增强发布产物整理能力
- 自动生成正式 zip 附件

### Release 资产

- 基于当前便携目录生成 zip 包
- 名称遵循版本与日期规范

### GitHub 元数据

- 创建 PR
- 创建 Release
- 编写中文发布说明

## 测试与验证

### 需要验证的内容

- `README.md` 能让首次访问者理解项目用途、功能和下载方式
- `README_portable.txt` 能让实验人员按步骤完成操作
- `build_release.ps1` 能稳定产出完整便携目录和 zip 附件
- Release 附件可直接下载并解压使用
- 既有测试仍保持通过
- 打包流程仍保持成功

### 不做事项

- 不在本次迭代中重构整体 GUI 风格
- 不新增官网、文档站或复杂品牌素材系统
- 不伪造 Moonlight/YOLO 那类项目的视觉资产，只做符合当前仓库条件的成熟开源呈现

## 交付结果

完成后应具备：

- 一个更像完整开源项目的 `README.md`
- 一个面向实验人员的中文便携版说明
- 一个可直接下载的 GitHub Release
- 一个规范命名的便携版 zip 附件
- 一个可追踪此次变更的 PR
